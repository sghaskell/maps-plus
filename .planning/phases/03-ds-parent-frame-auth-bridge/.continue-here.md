# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each constraint below is a structural boundary
> that will break Phase 3 if violated. Acknowledge each one explicitly before
> proceeding.

- [ ] CONSTRAINT: **Browser security boundary is not a client bug** — Root cause of Phase 02 UAT-2 is `SameSite=Lax` on null-origin cross-site subresource requests from `about:srcdoc`. No client-side code change (cookie flags, CORS headers, `fetch` credentials, tile-layer options, image crossorigin, etc.) can fix it. Only a parent-frame `postMessage` bridge resolves it. Do NOT propose client-only fixes.
- [ ] CONSTRAINT: **postMessage protocol is single-purpose, permanently** — Exactly one request type (`maps-plus:fetch-tile`) and one response type (`maps-plus:tile-result`). Optional ping/pong only for feature detection. Any extension (future cache warming, telemetry, error reporting, etc.) is a **new phase with its own threat model** — not an extension point added "while we're here."
- [ ] CONSTRAINT: **No secrets or identifiers in postMessage payloads** — Iframe → parent: tile coordinates + URL only. Parent → iframe: tile bytes + content-type only. No session tokens, no session IDs, no search data, no user identifiers, no app context, no CSRF tokens. Ever. In either direction.
- [ ] CONSTRAINT: **Phase 1 SSRF allow-list remains the trust boundary** — The bridge performs authenticated same-origin fetch against the already-validated Phase 2 proxy URL. It does not duplicate, extend, or replace the server-side allow-list. If someone proposes "let's validate URLs client-side too" as a second line of defense, fine for shape-rejection (DS-AUTH-04) but the server MUST still be authoritative.

**Do not proceed until all boxes are checked.**
