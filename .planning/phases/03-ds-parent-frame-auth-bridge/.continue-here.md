## R2 verdict (do not re-litigate)

Six vectors, all closed:

1. **Mako template overrides** — DS templates (`dashboard.html`, `example-hub.html`, `shared-dashboard.html`) hardcode their script tags and do not render any `customJsFiles` template variable. Per-app `appserver/templates/dashboard.html` cannot override DS's because DS's view XML uses fully-qualified `splunk-dashboard-studio:/templates/dashboard.html` paths.
2. **DS module / lifecycle pre-render hooks** — Bundle keyword sweep across ~11 MB of compiled React (boot bundle + 3 main chunks) returned zero hits for any extension/plugin/hook keyword. Internal `apiRegistry` (`registerVisualizationApi` etc.) is closed-over inside the React tree and not callable from outside.
3. **`viz.json` extension keys** — Custom-viz registry mapper (`oh` function in `chunk-J3STZZGT.js`) reads only a closed schema: `build, app, name, framework, cssUrl, jsUrl, formatter, label, dataSources, initialRequestParams, allowUserSelection, supportsDrilldown`. No `topFrameScript` or analogous field is honored.
4. **`setup.xml`** — One-shot configuration form handled by `admin.py`, not invoked by `view.py` on dashboard view. Out-of-band by design.
5. **Official documentation** — Splunk has not published a DS-equivalent of the SimpleXML-era `application.js` convention. Splunk Help articles explicitly warn against custom JavaScript in DS dashboards.
6. **Splunkbase pattern-mining** — Skipped; vectors 1–5 are conclusive on architectural grounds.

Empirical confirmation: rendered HTML for `/en-US/app/leaflet_maps_app/png_markers_copy` (a real DS dashboard inside the Maps+ namespace, captured to `/tmp/ds-rendered.html`) shows zero scripts from `leaflet_maps_app`. Only DS, system core, and Splunk first-party telemetry scripts load.

Side-quest result: DS iframe `sandbox="allow-scripts"` (no `allow-same-origin`), confirmed in `chunk-DT4FOOLP.js`. This pins the React-side decision (DS deliberately uses opaque-origin sandboxing for custom visualizations).

## R1 + R4 verdict (pre-collapsed — no separate empirical test required)

**R1's hypothesis** (per-app `application.js` auto-load fires on DS pages when the script lives inside the viewing app's `appserver/static/`) is structurally impossible because the DS templates do not render the `customJsFiles` template variable, even though `view.py:_getCustomFiles` does collect `application.js` from the viewing app's namespace. The empirical capture confirms it: zero scripts from `leaflet_maps_app` in the rendered HTML.

**R4's hypothesis** (per-app nav XML script include) is dead for two independent reasons: (1) DS rendered HTML has no nav DOM at all (DS renders splunkbar/appbar from React at runtime, not from per-app XML), and (2) the Splunk nav XML schema does not support `<script>` elements.

Both R1 and R4 are recorded in `03-RESEARCH-ADDENDUM.md` § R1 and § R4 with the relevant evidence pointers.
