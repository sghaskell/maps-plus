## R3 verdict (do not re-relitigate)

**Spec-confirmed not feasible.** The iframe gets a cross-origin `WindowProxy` reference to `top` and `parent`, but only the safe-listed properties (HTML §7.2.1.3.1: `window`, `self`, `location`, `close`, `closed`, `focus`, `blur`, `frames`, `length`, `top`, `opener`, `parent`, `postMessage`, plus array indices) are readable cross-origin. `document` is NOT on the list. Reading any non-safe-listed property triggers `IsPlatformObjectSameOrigin` (§7.2.1.1) → opaque ≠ tuple → SecurityError DOMException. The only legitimate channel is `postMessage`, which requires a pre-installed listener at the receiver — exactly the load-point dependency R3 was meant to dissolve.

**Empirical test was skipped — justified in addendum.** Spec is unambiguous, current browser behavior is uniform (SO Q78501355, 2026), and Phase 02 UAT-2's already-observed `Origin: null` header is downstream of the same opaque-origin boundary. Running the probe would not change the outcome. The probe stub files (`appserver/static/parent-auth-bridge.js`, `appserver/static/dashboard.js`, `default/data/ui/views/phase03_probe.xml`) **remain in place** as scaffolding for R1.

**Side finding worth recording:** The DS sandbox is almost certainly `sandbox="allow-scripts"` (without `allow-same-origin`) — only configuration consistent with both Phase 02 UAT-2's observed `Origin: null` AND Maps+ JS actually executing. R2 should opportunistically confirm the literal `sandbox=` value when inspecting Splunk Web's DS dashboard HTML (cheap — one `view-source:` grep; 30 seconds).

## R2 — live work item — execution guidance

### Central question

**Does Splunk 10.x DS v2 expose any extension point that runs in the top frame, before the custom-visualization iframe is constructed?**

If yes → that's where the parent-side `postMessage` listener gets installed, and the rest of Phase 3 (D-03 dispatch, D-04 regexes, D-NN-3 schema rename) is straightforward.

If no → Phase 3's stated goal (full DS parity from app space alone) is unreachable. The fallback options become: (a) ship a Splunk-app-installer that drops a hook into Splunk Web's own boot path (out of normal app scope; ugly and fragile across upgrades), (b) accept partial DS support (e.g., document a manual `setup.xml` step the operator runs once), or (c) declare DS unsupported and revisit when Splunk publishes a documented top-frame extension API. **Whichever conclusion R2 reaches, the evidence trail must be airtight** — a wrong "no" wastes Phase 4–5 reworking around a problem that was solvable; a wrong "yes" gets discovered as a failure during implementation.

### Candidate vectors to enumerate (rule each in or out with evidence)

This is a starting set, not exhaustive. R2 should expand as evidence surfaces.

1. **`appserver/templates/*` overrides** — Splunk Web supports per-app Mako template overrides (e.g., `appserver/templates/dashboard.html`). If Maps+ ships such an override for a DS-relevant template, it injects HTML into the top frame before the iframe is created. Question: which templates does Splunk 10.x DS v2 actually use for dashboard rendering, and are any of them per-app overridable?
2. **DS module pre-render lifecycle hooks** — DS v2 modules (custom visualizations, custom inputs) are registered via `viz.json` / module manifests. Some module systems expose lifecycle hooks (`init`, `setup`, `beforeRender`, `attach`) that may run in the host frame, not the iframe. Question: does DS v2's module loader call any registered callback before iframe mount?
3. **`viz.json` extension keys** — beyond the documented `module`/`name`/`label` fields, are there undocumented or under-documented extension keys (e.g., `topFrameScript`, `bootstrap`, `parent_setup`)? Splunk's source ground-truth (`splunk-web` JS bundle) is more authoritative than docs here.
4. **`setup.xml`** — legacy (Simple XML era) per-app one-shot setup file. May still execute in 10.x, possibly in the top frame. Question: does it run on dashboard view? Is it DS-aware?
5. **Splunk Web's pre-render hooks** — anything documented in Splunk's developer docs as "runs before dashboard renders" or "runs on dashboard load." Search `dev.splunk.com`, `docs.splunk.com/Documentation/Splunk/10.2.x`, and the Splunkbase developer portal.
6. **Splunkbase pattern-mining** — find apps that target DS v2 and have documented or visibly solved a top-frame load-point problem. **Pattern-match, do not blindly copy.** Useful searches: apps with `dashboard.js` that does non-trivial work; apps that ship `parent-frame.js` or `host.js`-named files; apps with `appserver/templates/` overrides; map/geo apps (likely face the same cookie issue with tile servers); apps that declare DS v2 compat in `app.conf` and ship anything beyond a viz registration.
7. **Side-quest (always do this regardless):** `view-source:http://localhost:8000/.../dashboard-with-maps-plus-viz` and grep for `sandbox=`. Confirm the literal sandbox attribute value on the DS iframe. Costs 30 seconds; informs all bridge design downstream.
