## Why UAT-2 is blocked (short version)

Dashboard Studio hosts custom visualizations inside an `about:srcdoc` iframe
with origin `null`. The browser refuses to send Splunk's `SameSite=Lax` session
cookie on subresource requests from `null` → `http://localhost:8000` (cross-site).
Every `/en-US/splunkd/__raw/services/maps_plus/tile/proxy?...` request arrives
cookieless; Splunkweb redirects to login. No client-side tile-layer refactoring
can overcome this — the authenticated request has to originate from (or be
authorized by) a frame the browser considers same-site with the Splunk Web host.

Full root-cause writeup and request-header evidence: `02-UAT.md § UAT-2`.

## What the browser does (the boundary that blocks UAT-2)

```
GET /en-US/splunkd/__raw/services/maps_plus/tile/proxy?url=...&z=6&x=14&y=24
Origin: null
Sec-Fetch-Site: cross-site
Sec-Fetch-Mode: no-cors
Sec-Fetch-Dest: image
(NO Cookie: header — SameSite=Lax blocks cross-site null-origin cookie send)

→ 303 See Other
Location: /en-US/account/login?session_expired=1&return_to=...
```

## Phase 03 design sketch (full detail in `02-UAT.md § Follow-ups`)

- Parent-window JS shim loaded via `app.conf` static-JS wiring
- postMessage RPC with a single message type: `maps-plus:fetch-tile`
  - request: `{ type, requestId, url, z, x, y, s?, r? }`
  - response: `{ type: 'maps-plus:tile-result', requestId, ok, blobBase64|status|code, contentType? }`
- Origin validation both ways (iframe verifies `event.origin` is top frame;
  parent verifies iframe is on expected Splunk Web origin)
- Parent does authenticated fetch (same-origin, session cookie present);
  SSRF defense still enforced by Phase 01 Python handler unchanged
- Iframe converts returned bytes to `blob:` URL and assigns to `img.src`
- Rate limiting on parent side; no extensible RPC surface; no tokens or search
  data in payloads

## Anti-patterns to avoid in Phase 03

- Do NOT try to solve UAT-2 by "fixing" client-side cookies, CORS headers, or
  tile-layer fetch options. The root cause is a browser security boundary
  (SameSite on null-origin cross-site subresources). Only a parent-frame
  bridge resolves it. Read `02-UAT.md § UAT-2` before attempting anything else.
- Do NOT extend the postMessage protocol beyond the single tile-fetch message
  type. Any generic RPC surface inside an iframe → parent bridge is a
  privilege-escalation risk.
- Do NOT pass session tokens, search data, or user identifiers in postMessage
  payloads. Tile bytes in one direction only.
